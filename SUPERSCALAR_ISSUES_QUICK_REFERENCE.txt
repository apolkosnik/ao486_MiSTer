4. WRONG MUTEX SOURCE FOR DEPENDENCY ANALYSIS  
   File: rtl/ao486/pipeline/dispatch.v
   Lines: 85-100
   
   Code:
   ----
   wire pipeline_mutex;
   assign pipeline_mutex = exe0_mutex | exe1_mutex | wr0_mutex | wr1_mutex;
   
   wire inst0_has_dependency;
   assign inst0_has_dependency =
       inst0_valid &&
       ((inst0_mutex[7:0] & pipeline_mutex[7:0]) != 8'b0 ||
        ...
   
   Issue:
   ------
   The dependency analysis uses inst0_mutex (what inst0 WILL SET) against
   pipeline_mutex (what's currently in flight). But it should check what
   inst0 will READ against what's being written.
   
   This is conceptually backwards:
   - inst0_mutex[EAX_BIT] = 1 means inst0 will WRITE to EAX
   - pipeline_mutex[EAX_BIT] = 1 means something in flight will write to EAX
   - Conflict only if inst0 READS EAX and something WRITES to it
   
   Current check doesn't determine if inst0 reads EAX or writes to EAX.

5. MISSING DUAL-INSTRUCTION PIPELINE INTERFACE
   File: rtl/ao486/pipeline/pipeline.v
   Status: Monolithic single-issue design
   
   Problem:
   --------
   pipeline.v outputs single instruction signals:
   - rd_cmd (7 bits)
   - rd_cmdex (4 bits)
   - rd_src_wire (32 bits)
   - rd_dst_wire (32 bits)
   
   But superscalar_pipeline.v expects dual instructions:
   - inst0_cmd, inst1_cmd
   - inst0_cmdex, inst1_cmdex
   - inst0_src, inst1_src
   - inst0_dst, inst1_dst
   
   This is a fundamental architectural mismatch that requires restructuring
   the entire pipeline to support dual-instruction flow.

7. MISSING MEMORY OPERATIONS IN DUAL EXECUTE
   File: rtl/ao486/pipeline/dual_execute.v
   Status: Not implemented
   
   Issue:
   ------
   The dual_execute module only handles ALU operations (ADD, SUB, MOV, etc.)
   It does not handle:
   - Load/Store operations
   - Memory addressing
   - Memory forwarding between instructions
   
   Both instructions cannot touch memory simultaneously.
   
   Would need:
   - Shared load/store queue or dual memory ports
   - Memory address translation for both instructions
   - Memory dependency tracking (inst0 writes, inst1 reads same address)
   - Cache conflict detection

---

8. EXCEPTION HANDLING FOR DUAL-ISSUE NOT DESIGNED
   Status: Not in any module
   
   Problem:
   --------
   Current ao486 has single-instruction exception handling:
   - execute.v triggers exception
   - write.v handles it
   - Pipeline resets
   
   With dual-issue, conflicts arise:
   - What if ALU0 raises divide-by-zero while ALU1 completes?
   - Which instruction's results are committed?
   - How to handle task switches mid-dual-issue?
   
   Needs:
   - Per-ALU exception tracking
   - Exception prioritization logic
   - Selective instruction retirement
   - Synchronization points in pipeline
